# Development

```bash
claude plugin validate .claude-plugin/plugin.json --strict
claude plugin validate .claude-plugin/marketplace.json --strict
claude plugin test .
```

`validate` on the plugin manifest reads it and the hooks module the way the engine will and reports what the module hooks and calls; on the marketplace manifest it checks the catalog. (With both manifests present, `validate .` checks only the marketplace.) `test` runs the files in `tests/` against the engine itself, on the terminal and desktop surfaces, including a character-for-character comparison with the fifty golden rows of the design specification. CI installs the Claude Code release pinned in `.github/workflows/ci.yml` and runs all three; bump the pin together with the version requirement above.

For hot reload while editing, start a session with `claude --plugin-dir .` from the repository root; saving a file reloads the module. In such a session `/plugin-types` writes the engine's declarations to `.claude-plugin/types/` (ignored by git); `npx tsc -p .claude-plugin/types/tsconfig.json` then type-checks the hooks and tests against them.

The design canvas under [`design/`](../design/README.md) is the source of truth for the look, with an interactive playground and every state on both themes; open `design/index.html` in a browser. It matches the shipped look: `━` cells in the terminal and smooth glowing bars on the desktop. Its boards open on ramp coloring; the plugin defaults to level coloring since 1.1.0, which the state boards show with `?bars=level`. The graphics on this page, the title and the terminal rows included, are generated by `design/readme/make.py` from the same palette and geometry; the terminal rows come from the builder itself, dumped to `design/readme/terminal-rows.json` by `node design/readme/rows.mjs` (Node 22.18 or later), which `node design/readme/rows.mjs --check` verifies. The pictures under [Every option at a glance](options.md) are drawn by `node design/readme/options.mjs` from the builder and `hooks/drawings.ts`; `node design/readme/options.mjs --check` verifies them, and CI runs it.

**Benchmarking** compares the desktop pulse of different versions of hooks/, on Windows. `headless.ps1` takes `-Base <ref>` (default `master`) and compares it with the working tree; `inapp.ps1` takes `-Sides`, any number of git refs, folders holding a copy of hooks/, and `work` for the working tree (default `master,work`). Both write only to `scripts/benchmarking/out/` (ignored by git):

```powershell
pwsh scripts/benchmarking/headless.ps1
```

```powershell
pwsh scripts/benchmarking/inapp.ps1
```

`headless.ps1` builds the pages with `pages.mjs`, loads one desktop band per version and look in headless Microsoft Edge, the engine the app draws with, and reports CPU and GPU (the median of three rounds), and how far the working tree's frames at rest, mid-pulse and peak are from the base's (`compare.mjs`); `-SkipBands` runs only the frames, `-SkipFrames` only the bands. `inapp.ps1` measures the desktop app itself: it installs each side's hooks/ into the installed plugin, switches options with `claude plugin configure`, which hot-reloads the plugin, and sums every `claude.exe` under `pulseMode: always` and with the pulse off; `-Repeat 3` takes turns between the sides three times and reports each one's median, which a comparison needs, since the app's own cost drifts by more than most changes save; `-Set @{ glow = 'false' }` adds options to every measurement, and `-Seconds` lengthens each from its 20 s. At the end it puts back the installed files and your options, or with `-KeepWork` leaves the working tree installed. Keep the app's window visible while it runs, and start it from a terminal or in the background so no session is busy: whatever a session does while it measures counts too, and only the app's own idle work, the floor with the pulse off, belongs in the numbers. The headless numbers are a guide; only the app's are the cost you pay.

**Releasing** happens in the pull request it ships with; nothing is tagged by hand:

1. Move the `[Unreleased]` entries of `CHANGELOG.md` into a new dated `## [x.y.z]` section, leave `[Unreleased]` empty, and update the compare links at the bottom.
2. Set the same `version` in `.claude-plugin/plugin.json` and `.claude-plugin/marketplace.json`.
3. Commit these with the change they release and merge the pull request.
4. On every push to `master` the `Tag Release` workflow (`.github/workflows/tag-release.yml`) reads the newest `## [x.y.z]` heading of `CHANGELOG.md` and, when the tag `vx.y.z` does not exist yet, creates it on that commit. A merge that only touched `[Unreleased]` creates nothing, and a new heading whose version `plugin.json` does not name fails the run before anything is tagged. It runs only in the repository `plugin.json`'s `repository` names, so a fork is never tagged.
5. It then calls the `Release` workflow (`.github/workflows/release.yml`), which checks that the tag matches both manifests and publishes the GitHub release with that version's `CHANGELOG.md` section as its notes. A `v*` tag pushed by hand runs it too, and creating the release in the GitHub UI first also works; the workflow then brings its notes in line with the changelog.

`master` is protected by the ruleset in `.github/rulesets/`: a pull request with a code owner's approval and a green `plugin` check, a linear history, no force-push or deletion. The repository admin bypasses it and can push or merge directly.
